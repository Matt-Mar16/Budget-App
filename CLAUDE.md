## THE LEDGER

### Layout
`budget_app.py` sits alone at the top of `ledger/` as the one entry point. Everything it imports — `finance_core.py`, `profiles.py`, `theme.py`, `crypto_utils.py`, `charts.py`, `inbox_sync.py`, `sync_inbox.py`, plus `README.md`/`requirements.txt` — lives in `ledger/src/`. `budget_app.py` adds `src/` to `sys.path` at the top of the file (`sys.path.insert(0, .../src)`) before its own imports, so every module inside `src/` keeps using plain `import finance_core`/`import profiles`-style imports unchanged, regardless of which script is the one actually invoked. `profiles.py`'s `APP_DIR` (where `Profiles/` lives) is computed two directories up from its own file — `src/`'s parent — since `Profiles/` itself deliberately stayed at the top of `ledger/`, not inside `src/`, so real per-profile data is never mixed in with source code. `tests/conftest.py` adds both `ledger/` and `ledger/src/` to `sys.path` for pytest, so test files keep importing `finance_core`/`profiles`/`budget_app` by bare name too.

### Commands
- Run the GUI: `cd ledger && python3 budget_app.py` (needs Tkinter; on Linux, `sudo apt install python3-tk` if missing)
- `budget_app.py`/`src/finance_core.py`/`src/profiles.py`/`src/theme.py`/`src/crypto_utils.py`/`src/charts.py` have no third-party dependencies — stdlib only (`tkinter`, `sqlite3`, `datetime`, `uuid`, `dataclasses`, `statistics`, `typing`, `os`, `re`, `hashlib`, `hmac`, `struct`). This is deliberate — don't add a dependency to the GUI app itself.
- `src/inbox_sync.py`/`src/sync_inbox.py` (phone-entry bridge, see below) need `openpyxl` — isolated in their own `ledger/.venv` (`pip install -r src/requirements.txt`) so the GUI stays dependency-free.
- Run the tests (from `ledger/`): `.venv/Scripts/python.exe -m pytest` (173 tests total across `tests/test_finance_core.py`, `tests/test_budget_app.py`, `tests/test_profiles.py`, `tests/test_inbox_sync.py`, as of the "look at all my notes" round below)

- Load phone-entered transactions and clear the inbox: `.venv/Scripts/python.exe src/sync_inbox.py --profile <slug>`

### Architecture
Layered, no service/repo indirection: `budget_app.py` (Tkinter UI, one tab class per screen) imports specific functions/classes from `finance_core` plus the whole `profiles`, `theme`, `charts` modules. `finance_core.py`/`profiles.py` are stdlib-only; `profiles.py` does lazy/local imports of `finance_core.Database` and `crypto_utils` to avoid import cycles and keep encryption fully opt-in.

The data layer is `finance_core.Database` (`finance_core.py:31`), wrapping one `sqlite3.Connection` and exposing ~70 CRUD/finance methods. Read-only aggregation (net worth, savings rate, safe-to-spend, payoff simulation, etc.) is separate: plain module-level functions that take a `Database` instance rather than methods on it.

UI tabs hold `self.app.db` and call `Database` methods directly — e.g. `TransactionsTab.add_transaction()` calls `finance_core.would_exceed_budget()` for the budget-enforcement warning, then `self.app.db.add_transaction(...)`, then `self.app.refresh_all()`.

**Entry point flow**: `if __name__ == "__main__"` builds `ProfileLauncher` (a `tk.Tk` subclass) and calls `.mainloop()`. Picking a profile calls `ProfileLauncher._open()`, which prompts for a password via `simpledialog` if the profile is locked (`profiles.unlock_profile()`), then builds `App(profile)` — this opens `Database(profiles.db_path_for(slug))`, runs `generate_due_recurring()`, and builds the sidebar/tabs. `switch_profile()`/`on_close()` explicitly call `db.close()` before destroying the window (a deliberate Windows file-lock fix — don't remove it).

### Key mechanisms (know these before touching financial logic)
- **Balance effects**: `_apply_balance_effect_nocommit()` (`finance_core.py:507`) is the single source of truth for how a transaction changes an account balance (asset vs. liability accounts move in opposite directions). Called from `add_transaction`, `generate_due_recurring`, `transfer_between_accounts`, and reversed manually inside `update_transaction`/`_delete_transaction_row_nocommit` — all four call sites must stay consistent if this logic changes.
- **Round-ups**: computed inline in `_apply_roundup_nocommit()` (525) on every negative-amount insert/edit/recurring post; reversed by looking up the `roundups` table by `transaction_id` on delete/edit.
- **Transfers**: `transfer_between_accounts()` (901) inserts two linked rows sharing a `transfer_group_id`, both `is_transfer=1`; cross-currency rate is frozen as `historical_rate` on the destination leg. A leg can't be edited directly (`update_transaction` refuses if `is_transfer`); deleting one deletes both unless `delete_transfer_pair=False`.
- **`is_transfer` exclusion**: `transactions_in_month(year, month, include_transfers=False)` (751) and `category_anomalies` filter out transfer legs by default — this keeps internal transfers out of savings-rate/safe-to-spend/budget/anomaly math, while `account_ledger()` (769) always includes them for the per-account statement view. Any new aggregate function needs to make the same choice explicitly.
- **Reconciliation**: `reconciled`/`reconciled_date` columns plus `_require_unreconciled()`/`reconcile_transaction()`/`unreconcile_transaction()` (480-505). `update_transaction`/`delete_transaction` raise `ReconciledTransactionError` unless called with `force_unreconciled=True`.
- **Profile encryption**: `crypto_utils.py` is a stdlib-only PBKDF2-HMAC-SHA256 + HMAC-SHA256-counter-mode cipher (hand-rolled, not independently reviewed — see README caveat). `profiles.lock_profile()`/`unlock_profile()` (224-252) swap `<slug>.db` ↔ `<slug>.db.locked`.
- **Recurring auto-post**: `generate_due_recurring(today)` (1068) runs at `App.__init__` and via `RecurringTab.post_due()`; loops while `next_date <= today`, applying balance/round-up effects and advancing via `_advance_date()` (1051), capped at 36 iterations per item.

### Phone-entry bridge (`inbox_sync.py` / `sync_inbox.py`)
Added 2026-08-08 as the first piece of a longer-term plan to make THE LEDGER a lifetime general-purpose budget tracker (superseding Trip Budget Tracker's Excel-only approach for that goal — Trip Budget Tracker itself is unaffected and still works standalone for this trip). Same phone-inbox pattern as Trip Budget Tracker, adapted to write into THE LEDGER's SQLite database instead of a CSV log:

- **`inbox_sync.build_inbox_workbook(db, path)`** — generates `Inbox.xlsx`: a `Transactions` table (`Date, Account, Category, Payee, Amount, Currency, Note`) plus `Accounts`/`Categories` reference sheets exported live from the profile's actual database, used as the dropdown source. Regenerate with `--build` whenever accounts/categories change.
- **`inbox_sync.sync_inbox(excel_path, db, backups_dir, now=None)`** — reads the inbox, resolves `Account`/`Category` names to THE LEDGER's internal IDs (raising a clear `ValueError` naming the bad value if a name doesn't match — same fix as Trip Budget Tracker's `account_running_balance`), backs up exactly what it read to `--backups-dir` (default `Profiles/inbox_backups/`), calls `Database.add_transaction()` per row (reuses THE LEDGER's own balance-effect/round-up logic, no duplicated math), then clears the sheet. Same safety philosophy as Trip Budget Tracker: backup-before-clear, no automatic dedup, validate-before-mutate (all rows are checked against known accounts/categories, and the backup is written, before anything is inserted or cleared).
- **`sync_inbox.py`** (CLI) — `--profile <slug>` targets a specific profile; if that profile is password-locked, prompts via `getpass` and unlocks it the same way the GUI does (`profiles.unlock_profile()`).
- The GUI (`budget_app.py`) is unchanged — this is a separate load step, run before opening the app to see new transactions. No combined single-command version yet (the `dashboard.py` equivalent for this) — deliberately deferred until the bridge itself is proven out.
- **Currency exchanges**: a `Category` value of `"Currency Exchange"` (also injected into the workbook's Categories dropdown, not a real DB category) marks a row as one leg of an exchange rather than a normal transaction. `sync_inbox()` groups these by `Date`, requires exactly 2 rows per date (one negative amount, one positive), and calls `Database.transfer_between_accounts(..., to_amount=...)` instead of `add_transaction()` — same linked-transfer/frozen-rate treatment the GUI itself now supports (see below). An unpaired or malformed exchange row raises a `ValueError` naming the date.
- **Core fix this surfaced**: `transfer_between_accounts()` previously had no way to record an actual observed destination amount — it always *computed* the destination amount from the stored `fx_rates` table, even though its own docstring claimed to freeze "the rate that actually applied." Added an optional `to_amount` param (`finance_core.py`): when given, it's used directly and `historical_rate` is computed from the real amounts on both legs instead of guessed from a possibly-stale rate. This is `finance_core.py`'s first-ever test coverage (`tests/test_finance_core.py`) — the file otherwise still has none. The GUI can pass `to_amount` too once/if a transfer-entry screen is updated to collect it; that UI change hasn't been made yet.
- **GUI transfer dialog updated** (`AccountsTab.open_transfer_dialog()`, `budget_app.py`): added an optional "Actual amount received" field. Left blank, behavior is unchanged (computed via `fx_rates`, same as before). Filled in, it's passed as `to_amount` to `transfer_between_accounts()`, and the rate preview label switches to show the real rate derived from what you typed instead of today's stored rate. The GUI has no test suite (documented, pre-existing) so this was verified by launching the app and confirming a clean start with no traceback, plus a source parse check — not a full interactive/visual check, since there's no screenshot tooling available for native Tkinter windows in this environment. Worth clicking through by hand before trusting it fully.
- **Holiday/home currency mode** (`App.currency_mode()`, `budget_app.py`): a `currency_mode` setting (`"home"` default / `"holiday"`), toggled from a combobox in `SettingsTab`. Purely a UI simplification — `home` hides the FX Rates card and the per-account currency picker on Add Account (new accounts silently default to the reporting currency); `holiday` shows both. No data is affected either way — every account/transaction still has a real currency underneath, switching modes never reinterprets existing data. Verified with a throwaway headless script (`App` instantiated directly, `refresh_all()` called, widget visibility asserted in both states, profile + script deleted after) rather than clicking through manually, for the same no-screenshot-tooling reason as the transfer dialog above — this caught two real bugs before they shipped: `winfo_ismapped()` doesn't reflect pack state without a running event loop (switched to a tracked `_fx_visible` flag), and only the initially-shown tab gets `.refresh()` called at startup (not a bug, just something the smoke script had to account for).
- **Not yet done**: the inbox workbook still needs to be placed under a OneDrive-synced path for phone entry to actually reach it (same blocker as Trip Budget Tracker, not yet resolved).

### Scrollable tabs
Every tab (`ScrollableTab` base class, `budget_app.py`) scrolls cleanly now — mouse wheel when hovering, scrollbar always visible. The trick: a tab's `self` is embedded into a `Canvas` via `create_window` instead of being gridded directly into the page container, so every existing `_build()` method keeps using `self` as the widget parent completely unchanged — only `grid()`/`tkraise()` are overridden to act on the canvas+scrollbar wrapper. Verified headlessly (no screenshot tooling for native Tkinter here): instantiated `App` directly, called `show_page()` on all tabs, asserted each wrapper is gridded and its canvas picked up a real scrollregion.

### Cashback auto-invest
`accounts.cashback_auto_invest_account_id` (nullable FK to another account) lets a credit card route its earned cashback straight into an investment account's cost basis instead of sitting unredeemed for manual `redeem_cashback()`. In `add_transaction()`, when a card with this set earns cashback, it's immediately applied via the same balance+contributions update `add_investment_contribution()` uses (inlined rather than calling that method directly, to stay inside one atomic `with self.conn:` block rather than nesting transactions) and the transaction is marked `cashback_redeemed=1` on insert. Configured per-card from the Net Worth tab's credit card section ("Set Auto-Invest" button, `NetWorthTab._set_cashback_auto_invest()`). `update_account_details(..., cashback_auto_invest_account_id=0)` clears it back to no target — passing `0` (not `None`, which means "don't touch" like every other param on that method) gets translated to SQL `NULL` internally, since account ids start at 1 and the column has an FK constraint that would otherwise reject a literal `0`.

### Investments tab — capital gains (`InvestmentsTab`, `TaxTab`, `budget_app.py`)
New `security_lots` table (account_id, security, date, action buy/sell, quantity, price, fees, realized_gain) tracks individual buy/sell transactions per security, separate from the account-level `investment_contributions`/`investment_valuations` tables (which stay purely cash-in / mark-to-market and are unaffected). `Database.add_security_transaction()` and the capital-gains methods implement **plain UK Section 104 average-cost pooling only** — every buy/sell of a security within one account pools into a single running average cost via `_recompute_realized_gains_nocommit()`, which replays the full history in date order on every insert (cheap at personal-portfolio data volumes, and the only way to stay correct when a backdated transaction is entered after a later sell — verified by a dedicated test). **HMRC's same-day and 30-day "bed and breakfast" matching rules are NOT implemented** — both must apply before pooling for a fully correct UK CGT figure; this is flagged in the Tax tab's own UI copy, not just here.

`InvestmentsTab`: manual entry form, CSV import (stdlib `csv` module only — Excel/PDF import deliberately not built, since that would mean adding a third-party dependency like `openpyxl` to `budget_app.py` itself, breaking the documented stdlib-only constraint; if wanted later, follow the `inbox_sync.py` pattern of an isolated `.venv`-based script instead), current holdings per security (qty/avg cost/pool cost via `security_pool_state()`), and this-tax-year realized gains (`realized_gains_for_uk_tax_year()`, UK tax year = 6 Apr–5 Apr via `uk_tax_year_start()`).

`TaxTab`: net realized gain for the current UK tax year vs. a **user-editable** CGT annual exempt amount (`cgt_annual_exempt_amount` setting, defaults to 3000 but is not guaranteed current — HMRC changes this figure; verify and update it yourself) → estimated taxable gain. Carries an explicit disclaimer that this isn't tax advice.

Both tabs verified headlessly only (same no-screenshot-tooling limitation as the rest of the GUI): instantiated `App`, added a real investment account, added a transaction through the tab's own `add_transaction()`, imported a CSV through `import_csv()` with `filedialog`/`messagebox` mocked out (a real `messagebox.showinfo` blocks forever waiting for a click when run headlessly — this is what caused the first smoke-test attempt to hang and get killed), and asserted the resulting pool state.

### Research: other budgeting apps (feature gaps)
Looked at YNAB, Monarch Money, Copilot, Empower, Kubera, and general 2026 "best budgeting app" coverage. **Subscription-specific tracking**, **overspend run-rate projection**, and **multi-month/year trend views** were identified here and are now built (see the expense-tracking round below). ### Expense-tracking feature round
A batch of pure expense-tracking features, deliberately scoped narrower than the full "Personal Finance & Markets Hub" vision in `personal-finance-hub-features.md` (a separate, much larger aspirational document at the repo root covering trading/quant, IB valuation, asset management, risk, and macro tools for a student finance/trading portfolio — out of scope for THE LEDGER, which stays focused on daily expense tracking; those other areas are meant to get their own separate dashboards later, unified under a future master dashboard).

- **Emergency fund calculator** — turned out to already exist (`finance_core.emergency_fund_ratio()`, shown on the Dashboard metrics grid as "Emergency Fund: X.X mo"). No new build needed.
- **Overspend run-rate projection** — `finance_core.budget_run_rate(db, year, month, today=None)` projects each budgeted category's month-end spend from spend-so-far ÷ days-elapsed × days-in-month, built on `category_budget_status()`. Shown per-category in `BudgetsTab` ("On pace for £X" / "over by £Y" in `Bad.TLabel` style when projected to exceed budget).
- **Budget threshold alerts** — `finance_core.categories_over_threshold(db, year, month, threshold_pct=None)` (default from the new `budget_alert_threshold_pct` setting, itself defaulting to 80, editable in `SettingsTab`). Surfaced as lines in the Dashboard's existing flags/nudges panel (warn-styled once actually over, info-styled once past the threshold).
- **Dashboard trend range selector** — `monthly_history()` already supported an arbitrary `n_months`; only the UI was fixed at 6. Added a Combobox (6/12/24/36 months) next to the income-vs-expenses chart. Fixed a real pre-existing bug this surfaced: `monthly_history()`'s month labels used bare `"%b"` (e.g. "Jan"), which silently collided across different years once a range exceeds 12 months — now switches to `"%b '%y"` labels once `n_months > 12`.
- **New Insights tab** (`InsightsTab`, between Tax and Rewards in the nav) — **top payees** (`finance_core.top_payees()`, ranks this month's expense payees by total spend, rendered via the existing `charts.draw_bar_chart` reused as a single-series ranking) and a **spending heatmap by day-of-month** (`finance_core.daily_spend_totals()` + new `charts.draw_calendar_heatmap()`, a from-scratch calendar-grid chart reusing the existing `rounded_rect`/`lerp_color` helpers — no heatmap chart existed before). Both read off the app's shared `view_year`/`view_month` selector, same as Budgets/Dashboard.
- **Automatic subscription/recurring-charge detector** — `finance_core.detect_recurring_candidates(db, min_occurrences=3, interval_tolerance_days=6)` scans *actual transaction history* (not the manually-curated `recurring` table) for payees charging at regularly-spaced intervals, flags a price change between the two most recent occurrences, and skips payees already tracked in `recurring` (case-insensitive match). This is a genuinely separate mechanism from the Recurring tab's own deterministic date-rollforward posting — confirmed no overlap before building. Surfaced as a "Detected Subscriptions" card at the top of `RecurringTab`, each with an "Add to Recurring" button that pre-fills the existing Add form (name/payee/amount/currency/frequency inferred from the interval/next-date estimate) rather than saving directly, so a bad detection can be edited or ignored before it's tracked.
- **CSV import duplicate detection** — THE LEDGER already had a full staged-preview-commit CSV import pipeline (`csv_import_preview`/`csv_import_staged_rows`/`csv_import_commit`/`csv_import_discard`, backing `TransactionsTab.import_csv()`) — this was discovered mid-design and not rebuilt. Added: a `likely_duplicate` column on `import_staging`, set during `csv_import_preview()` by matching `(account_id, date, amount)` against existing `transactions`. The preview dialog now shows a "Duplicate?" column and pre-selects likely-duplicate rows for exclusion on Commit — but, matching this repo's established "no automatic dedup" philosophy (see Trip Budget Tracker's `sync_transactions.py` below), `csv_import_commit()` itself never silently drops a row; skipping only happens via the explicit `skip_row_ids` the UI passes from the (editable) pre-selection. This is the real use case for pulling in a bank statement export without duplicating what was already phone-entered.
- **Statement/report export** — a second, richer CSV export (`export_transactions_csv_full`, with account/transfer/reconciled columns) already existed in `finance_core.py` but was never wired to the UI; it's now a "Export Full CSV…" button next to the existing "Export CSV…" in the Transactions toolbar. New `finance_core.export_account_statement_csv(db, account_id, path)` wraps `account_ledger()` (already had a running-balance column) into a single-account, newest-first CSV — closer to an actual bank statement, wired as "Export Statement…" next to "View Ledger…" in `NetWorthTab`, intended as lightweight proof-of-funds documentation for the Canada visa/immigration process. **PDF export was not built** — same reasoning as the Investments tab's CSV-only import: a PDF library would be a new third-party dependency, breaking `budget_app.py`'s deliberate stdlib-only constraint.
- **Split transactions** — new `transaction_splits(id, transaction_id, category_id, amount, note)` table, reporting-only: the parent transaction row is untouched for balance/roundup/cashback purposes (still moves the full amount), splits only change which category(ies) the spend is *attributed* to for budgeting. `Database.set_transaction_splits(tx_id, splits)` validates the split amounts sum to the parent's amount (raises `ValueError` otherwise) and replaces any existing splits atomically; an empty list un-splits. A new shared helper, `finance_core._category_spend_entries()`, explodes split transactions into per-category amounts and is now the single code path both `category_budget_status()` and `spend_by_kind()` use (previously each duplicated its own raw iteration over `transactions_in_month()` — refactored together with this feature since both needed the same split-awareness). UI: "Split Selected…" in the Transactions toolbar opens a dialog with add/remove category+amount rows (pre-filled from existing splits, or the transaction's own category+amount as a starting point); the transactions list shows "⑃ split (N)" in the category column when applicable.
- **Tags** — new `tags(id, name)` + `transaction_tags(transaction_id, tag_id)` junction table, cross-cutting labels separate from category (e.g. "Canada Trip", "reimbursable", "work"). `Database.set_transaction_tags(tx_id, tag_names)` creates unknown tags on the fly and reuses existing ones by name. UI: a comma-separated "Tags" field on both the Add form and the edit dialog (`open_transaction_edit_dialog`), a "Tags" column in the transactions list, and the existing search box's haystack now includes tags — so searching "Canada Trip" finds every tagged transaction without a dedicated filter UI.
- **Reimbursement/IOU tracking** — new `reimbursements(id, transaction_id, owed_by, amount, status, settled_date, note)` table. `Database.add_reimbursement()`/`settle_reimbursement()`/`list_outstanding_reimbursements()`/`get_reimbursements_for_transaction()`. UI: "Mark as Owed…" in the Transactions toolbar opens a dialog (owed-by/amount/note, amount defaults to the transaction's full amount) against the selected transaction; an "Outstanding Reimbursements" card below the transactions list shows every pending entry with a "Mark Settled" button. Intended for splitting bills/rent with housemates while living in Canada.
- All of the above (schema additions, `Database` methods, and module-level aggregation functions) were built test-first — see `tests/test_finance_core.py` (49 tests total for `finance_core.py` after this round). GUI wiring was verified with headless smoke scripts per the established pattern (construct `App` directly, drive tabs/dialogs in code, assert on state, mock `messagebox`/`filedialog`), including a final combined smoke test that builds a realistic dataset touching split+tags+reimbursement+cashback+recurring-detection together and exercises all 11 tabs in one session. One genuine headless-testing gotcha surfaced and is worth knowing for future GUI test scripts: **a `ttk.Entry`/`ttk.Combobox`'s `.get()` can return a stale/empty value if its `textvariable` was set programmatically before the widget was ever mapped and no event loop has run** — the underlying Tcl variable is correct (verify with `root.getvar(widget.cget('textvariable'))` or read the Python `tk.StringVar` directly, which is what the app's own `do_save()`-style handlers do), so this is a test-harness-only artifact, not a production bug; real user interaction runs through a live `mainloop()` and doesn't hit it.

### Grouped/collapsible sidebar + hideable tabs
Prompted by a structural navigation audit (brainstormed with the visual-companion mockup tool — three sidebar options compared side by side; grouped-with-collapsible-section won). `NAV_ITEMS` (a flat 11-item list) became `NAV_GROUPS` (`budget_app.py`): a "Daily" group (Dashboard, Transactions, Budgets, Insights) that's always expanded, and a "Planning" group (Recurring, Debt Planner, Net Worth/FI, Investments, Tax, Rewards) that starts collapsed behind a "PLANNING ▸ 6" toggle row — click to expand in place. `NAV_ITEMS` still exists, derived by flattening `NAV_GROUPS` plus `SETTINGS_NAV_ITEM`, since a few places (the page-title lookup, the Settings checklist) want the full flat list. Settings itself moved out of the group list into its own pinned sidebar footer row, above "Switch Profile" — it's a set-once destination, not a daily one, and needed to stay reachable regardless of what's hidden.

New alongside this: **per-tab visibility**. A `hidden_nav_tabs` setting (comma-separated keys, same `get_setting`/`set_setting` pattern as `currency_mode`) lets you hide any tab except Dashboard and Settings (`PROTECTED_NAV_KEYS = {"dashboard", "settings"}` — enforced defensively in `get_hidden_nav_tabs()` itself, so even a hand-edited or stale setting value can never hide either). A new "Customize Navigation" card in `SettingsTab` lists a checkbox per hideable tab; unchecking and saving calls `App._build_nav_buttons()` to re-render the sidebar immediately (no restart needed), and redirects to Dashboard if you happened to be sitting on a tab you just hid. If hiding tabs empties the Planning group entirely, its header disappears too rather than showing an empty collapsible section.

Three small pure functions carry the actual logic — `get_hidden_nav_tabs(db)`, `set_hidden_nav_tabs(db, keys)`, `visible_nav_groups(nav_groups, hidden_keys)` — deliberately factored out so they're genuinely unit-testable without Tkinter, unlike the rest of `budget_app.py`. ### Per-profile folders + two-way editable CSV sync
Each profile now lives in its own subfolder — `Profiles/<slug>/profile.db` instead of the old flat `Profiles/<slug>.db` — so a profile's editable CSV exports (below) can sit right next to its database instead of every profile's files being dumped into one shared folder. `profiles.py`'s `_migrate_flat_profiles()` runs at the top of every `list_profiles()` call and transparently moves any old flat `.db`/`.db.locked` file into `Profiles/<slug>/profile.db` — existing profiles keep working with no action needed. `delete_profile()` now removes the whole subfolder (`shutil.rmtree`), not just one file, since a profile's data is the whole folder now.

Four CSV files per profile — `transactions.csv`, `accounts.csv`, `categories.csv`, `investments.csv` — for bulk editing outside the GUI and for backfilling historical data (phone-entered/AI-assisted loading of old records, the original motivation). Each has an `id` column: blank = new row, a real id with edited fields = an edit, a real id that existed before but is now missing from the file = a deletion. Two explicit buttons in a new "Data Files" card in `SettingsTab` — nothing syncs automatically in either direction:
- **`finance_core.refresh_profile_csvs(db, profile_dir)`** — regenerates all 4 files from current data. Read-only with respect to the database.
- **`finance_core.apply_profile_csvs(db, profile_dir, db_path)`** — backs up `profile.db` to `<profile_dir>/csv_sync_backups/profile_<timestamp>.db` first, then applies all 4 files in a fixed order (`accounts.csv`, `categories.csv`, `transactions.csv`, `investments.csv` — accounts/categories first, so a brand-new account or category referenced by name in the same transactions.csv pass already exists by the time it's needed), and returns one combined `{"added", "edited", "deleted", "skipped": [...]}` report shown to the user afterward.

Per-file apply functions (`apply_transactions_csv`, `apply_accounts_csv`, `apply_categories_csv`, `apply_investments_csv`) route every change through the same methods the GUI itself uses (`add_transaction`/`update_transaction`/`delete_transaction`, `add_account`/`update_account_core`/`update_account_balance`, `add_category`/`update_category`, `add_security_transaction`/`update_security_transaction`/`delete_security_transaction`) — never raw SQL — so balances, round-ups, cashback, and realized-gains recomputation all stay correct. Transfer legs, reconciled transactions, and split transactions are exported for visibility (a `status` column flags them) but are protected: `apply_transactions_csv` skips any edit to one and — critically — never deletes one just because its row is missing from the file, since editing those directly would bypass rules enforced elsewhere (a transfer's two linked legs, a locked reconciled row, a split's category breakdown). `accounts.csv`/`categories.csv` support add+edit only, deliberately no delete-by-omission — both are referenced by other tables via id, and a blank row would have no clean undo. `investments.csv` supports full add/edit/delete, since nothing else references a `security_lots` row by id.

**Two real data-loss bugs were caught by TDD before ever running against real data**, both the same shape: in `apply_transactions_csv` and `apply_investments_csv`, an unrelated validation error on an *existing* row's edit (e.g. a typo'd account name) caused that row's id to never be added to the "seen" set used to detect deletions — so a mere typo would make the row look like it had been intentionally removed from the file, and it would get silently deleted on the next apply. Caught by writing a regression test for exactly this scenario (`..._does_not_delete_an_existing_row_whose_edit_has_a_typo`), watching it fail, then fixing the ordering so an id is resolved and marked "seen" *before* any other field validation runs, in both functions.

Verified against the real profiles on disk: migration re-confirmed intact (`demo_sample_data`: 8 accounts/69 transactions, `matt`: 1 account/214 transactions, both unchanged), then `refresh_profile_csvs` run for real against both (safe — export-only, never touches the database) and the generated CSVs spot-checked for correctness. **A separate, unrelated bug in a throwaway smoke-test cleanup script** (`shutil.rmtree(os.path.dirname(profile_dir))` — the `dirname()` call resolved to the whole `Profiles/` folder instead of the one test subfolder) **actually deleted the real `Profiles/` folder mid-session**; caught within seconds via an immediate post-cleanup check, and fully restored from a `Profiles_backup_<timestamp>/` snapshot taken at the very start of this task, with the restored transaction/account counts re-verified to match exactly. Both `Profiles_backup_20260812_172011/` (pre-restructure) and a second post-restore backup sit at the top of `ledger/` — worth keeping until this feature's been used for real and trusted; safe to delete after that whenever you like. Test scripts from here on always target an isolated `profiles.APP_DIR` override rather than any path derived from the real `Profiles/` folder.

All commands below assume `cd trip-budget` first (or prefix paths with `trip-budget/`).
- Install deps: `.venv/Scripts/python.exe -m pip install -r requirements.txt` (pandas, openpyxl, matplotlib, plotly, pytest)

- Run a single test: `.venv/Scripts/python.exe -m pytest tests/test_finance.py::test_budget_vs_actual_flags_overspend_and_computes_remaining`
- Daily use — load new entries, report, clear the sheet, all in one step: `.venv/Scripts/python.exe dashboard.py`

- Just regenerate the report + charts (no sync): `.venv/Scripts/python.exe analyze.py`
- Regenerate a fresh workbook: `.venv/Scripts/python.exe build_template.py --out "Data.xlsx"`

All scripts accept `--excel` / `--log` / `--charts-dir` / `--backups-dir` overrides; defaults assume everything sits in `trip-budget/` alongside `Data.xlsx`.

### Architecture
Built test-first (TDD — every function in `finance.py`, `build_template.py`, `sync_transactions.py`, and `dashboard.py` was written test-first). The whole design turns on one idea: `Data.xlsx`'s `Transactions` sheet is a **transient inbox**, not the permanent record.

```
[Phone/laptop] --Excel entry--> Data.xlsx Transactions table (cleared after each sync)
                                        |
                              sync_transactions.py: read -> backup -> append -> clear
                                        |
                              data/transactions_log.csv (permanent, append-only)
                                        |
                              analyze.py: reads log + Accounts/Categories sheets -> report + charts
```

- **`finance.py`** — pure calculation functions only, no I/O: `parse_label` (splits a `"Category (Currency)"` dropdown label back apart), `load_transactions_log`, `budget_vs_actual`, `account_running_balance`, `effective_exchange_rate` (aggregates both currency legs of every exchange independently — deliberately never pairs individual rows), `sankey_flows`, `is_below_threshold`.
- **`build_template.py`** — generates the workbook: `Accounts`/`Categories`/`Transactions` sheets, the `Categories.Label` helper column (`=Category & " (" & Currency & ")"` — except the `Currency Exchange` row, which is a literal string override, since its blank Currency cell would otherwise make the formula render `"Currency Exchange ()"`), and the `Transactions` table's dropdown validations plus one example row carrying the `XLOOKUP` currency auto-fill formula (Excel's table "calculated column" auto-fill requires at least one existing row with the formula to propagate it to new rows the user adds).
- **`sync_transactions.py`** — the only script allowed to write to the Excel file. Deliberately has **no automatic dedup**: a content-based fingerprint would silently drop legitimate same-day duplicate transactions (e.g. two identical coffees); safety instead comes from the backup-before-clear ordering, recoverable by hand from `data/backups/` if a sync is ever interrupted.
- **`analyze.py`** — `build_report()` wires every `finance.py` function together into one dict (budget vs. actual per currency, account balances, low-balance flags, exchange rate, Sankey flows); `print_report()` / `draw_bar_charts()` / `draw_sankey()` are thin presentation layers over that dict.
- **`dashboard.py`** — daily-use entry point: calls `sync_transactions.sync()` then reuses `analyze.py`'s `build_report()`/`print_report()`/`draw_bar_charts()`/`draw_sankey()` against the freshly-updated log, so one command loads new entries, reports, and clears the sheet. `sync_transactions.py` and `analyze.py` remain usable standalone for just one half of that.
- Reference data (`Accounts`/`Categories` sheets) is read straight from the Excel file on every `analyze.py` run — only the `Transactions` sheet is ever treated as transient/clearable.

Full spec and the design rationale (why the inbox resets, why there's no dedup, the Sankey node/link model) live in `budget-tracker-plan.md`; day-to-day usage instructions are in `TRIP_BUDGET_README.md`.

### Known gaps
- **No `.gitignore` and not currently a git repo** — `.venv/`, `__pycache__/`, and `data/backups/*.csv` (which may contain real spend history) have no version control or exclusion rules if git is ever initialized here.
- **Excel file locking**: `sync_transactions.py`/`dashboard.py` open `Data.xlsx` with `openpyxl.load_workbook` / `wb.save` — if the file is open in Excel (desktop or, per OneDrive co-authoring, sometimes mobile) at sync time, the save can fail or conflict. Not handled or documented as a caution.
- **Currently hardcoded to exactly two currencies (GBP/CAD)** in a few places — e.g. `effective_exchange_rate()` and the Sankey flow builder assume exactly one GBP-side and one CAD-side leg per exchange. Generalizing to an arbitrary number of currencies/accounts (needed for reuse as a general ongoing budget, not just this one trip) is a real design change, not yet started.
- No validation step confirming the phone/laptop OneDrive round-trip actually works (the plan's own Build Order step 4 — "add a test row on the phone, confirm it appears on the laptop copy" — has apparently not been done, consistent with the workbook still holding only placeholder data).
- Everything under "Stretch" in `budget-tracker-plan.md` is still unbuilt: manual balance check-ins/mismatch flagging, run-rate overspend projection, market-rate FX comparison, multi-month trends, bank CSV import, recurring-payment detection.
